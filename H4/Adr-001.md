# ADR-0001 TIENDA DE ALIMENTOS
# Adapter + Observer, para cobrar y notificar una venta
## Contexto

Para confirmar una venta, se necesita cobrar con una pasarela externa y avisar a los interesados inventario y cliente, pero si el cobro fue realizado exitosamente, la Venta termina conociendo el SDK externo y la clase reacciona y notifica avisando de un pago exitoso o fallo en el pago.

## Decisión

AdaptadorPasarelaTarjeta, traduce el cobro hacia SDK externo que es Venta :: confirmar() solo llama a notificar() si el Adapter devolcio true, Un patron controla si el otro se ejecuta.

## Alternativa descartada

Usar Adapter y Observer aislados, como en los ejercicios con-adapter y con-observer, se plasman en con-observer/venta.php, confirmar() dispara notificar() sin verificar ningun resultado de pago.
No hay pago que aprobar, se entiende que la venta dada. Si se unieran ambas carpetas sin modificar nada, cualquier venta notificaria a los 3 observadores aunque el cobro no fuera exitoso.

## Patrones como podrian usarse y por que no se usaron

**Factory** 
ProcesarPago crear segun el tipo de pago(efectivo, tarjeta, transferencia), como ya hace con-factory.
No se uso en esta fusion por que Factory resuelve un problema previo, no el problema que tenemos actualmente (que hace una vez que el pago ya se intento) por que no habria deppendencia de flujo con Observer

**Strategy**
Podria calcularse el descuento antes de realizar cobros como con-strategy, no se aplico por que el dedscuento y la notificacion son independientes entre su: ninguno necesita el resultado de otro para funcionar

**Decorator**
Podria realizarse con el comprobante en capas de descuento, mensaje promocional, No se uso por que en esta fusion el comprobante lo arma directamente NotificadorCliente, agrega capas no cambia si se notifica o no.

**Builder**
para construir venta paso a paso antes de confirmar una venta, nose uso porquie Builder resuelve antes como se arma el objetivo y en el problema planteado se  arma despues, etapas distintas de ciclo de vida de la venta.

## Riesgos y prioridades

**Priorizamos**
Se priorizo notificar al cliente, descontar stock, que ocurra sie lpago fue rechazado, L integridad del flujo de cobro pesa mams que sumar flexibilidad con los patrones

**Arriesgamos**
Al no combinar factory en esta misma fusion AdapterPasarelaTarjeta, queda como el unico medio de pago dentro de final, si mañana se realiza una fusion necesita elegir entre varios procesadores, habria que agregar factory sobre lo que ya se tiene, hoy ess flexibilidad no esta resuelta.

## Consecuencias
**Pago:** 
Venta::confirmar(). ahora conoce dos cosas a la vez (cobrar y notificar) en vez de una sola, con una responsabilidad mas que en las versiones aisladas. Lo acepto porque sigue delegando el trabajo real a cada patron, solo orquesta el orden, no implementa ni el cobro ni las notificaciones.
